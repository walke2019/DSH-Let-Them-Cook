# P52 自动建群与真实任务调度边界

## 背景
在 Agent 群聊里派发“补齐中/英文业务功能”的真实开发任务时，消息中包含“角色/工作流/确认后写入”等业务词，被自动配置入口误判为重新生成角色与工作流草案，导致没有进入主 Agent / SubAgent 执行链。

## 修复
- `classifyAutoSetupIntent()` 增加执行语境保护：
  - `@角色 ...` 的消息直接交给调度器；
  - 包含“进入真实开发流程 / 当前工作流 / 启动第一阶段 / 检查 / 补齐 / 修复 / 测试 / 验收 / 派发”等执行动词时，不触发自动建群草案；
  - 已有待确认草案时仍保留“确认创建 / 取消创建 / 补充修改”的草案流程。

## 验收
- 创建类消息仍能生成草案；
- 确认类消息仍能写入当前工作区；
- 真实执行任务不会被草案入口吞掉。

## 追加发现：真实任务 brief 被阶段描述覆盖

实测中 commander 分派后，backend 回复偏泛化，原因是 `createTurnAssignment()` 在命中 ready workflow task 时使用阶段任务描述覆盖了真实用户消息。已改为：真实消息/上游分派在前，工作流阶段任务作为附加上下文，避免 SubAgent 只看到抽象阶段说明。

## 追加发现：长任务首个 @ 应作为接单人

P52 浏览器复测中，`@commander ... 请只分派 @writer ...` 仍被 workflow 当前阶段扩散到 backend/frontend。已改为：长任务如果消息开头就是某个角色的 mention，则初始只唤醒该角色；后续 SubAgent 由该角色在群聊内显式 @ 分派，匹配“主 Agent 先接单、SubAgent 再干活”的产品边界。

## 暂记 TODO
热重载后 API 中 `messages` 可能为空但 `assignments` 仍存在，说明消息记录未跟随工作区状态持久化；这会影响刷新后的复盘体验，后续需补独立消息持久化或统一 room/messages 存储。
